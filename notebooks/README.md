## The point: from raw observations to conclusions, all in Python

You can already do a lot of small-body science in Python without PyRoOrb. ASSIST and REBOUND
will integrate an orbit through the 2029 Apophis flyby with the planets, the Moon and the
large asteroids included. What they need, though, is an orbit to begin with: a state vector
and covariance **imported from JPL, the MPC or another orbit provider**. That orbit is a
finished product. It was fitted to the observations the provider had when it was computed,
weighted and screened the provider's way, and you cannot change any of that from where
you sit unless you use another OD tool and export results to import into Python, which introduces friction, troubleshooting, etc.

PyRoOrb starts one step earlier, at the observations themselves. The fit is a Python function
call, and the observations are an ordinary Python list of records that you can change before
any fit. That makes questions like these routine:

- **The published orbit is out of date.** New observations arrived last night, or someone
  recovered the object after years, and the provider has not refitted yet. Fetch the current
  astrometry and fit it yourself.
- **How much does the result hang on any one tracklet?** Refit with each night left out in
  turn, or drop two tracklets at random a few hundred times. Then see whether the
  close-approach distance, the Yarkovsky drift or the
  bound/unbound verdict holds steady, or whether it all rests on one night from one station.
- **Suspected blunders.** Leave out the observations you don't trust and see what moves.
- **A proposed archival observation or a remeasurement.** Add the precovery, or swap in the
  remeasured positions, and see whether the orbit agrees with them and what they do to the
  prediction. [Notebook 04](04_apophis_remeasured_2004.ipynb) does exactly this for five 2004
  Apophis positions.
- **What did we know then?** Cut the arc at a date and replay the discovery night by night
  ([03](03_short_arc_neo.ipynb)). Turn a force model on and off and see what it explains
  ([05](05_comet_nongrav_tempel2.ipynb), [12](12_ceres_encounter_perturbers.ipynb)). Add or
  remove the radar ([07](07_radar_leverage.ipynb)).

Without the fit in Python, every one of these is a round trip. You edit the observation file
by hand, run Find_Orb or OrbFit, and export the state vector and covariance matrix. Then you
read them into Python, propagate them with ASSIST, and start over for the next variant. A
bootstrap of a few hundred refits that way becomes a scripting project built around two
programs' file formats. In PyRoOrb it is a loop:

```python
import random
import pyroorb

obs = pyroorb.fetch_observations("2024 MK")

def tracklet(o):                      # one station's night (UTC noon to noon)
    return (o["obscode"], int(o["jd_utc"]))

tracklets = sorted({tracklet(o) for o in obs})
distances = []
for trial in range(200):
    drop = set(random.sample(tracklets, 2))          # leave two tracklets out
    subset = pyroorb.Observations([o for o in obs if tracklet(o) not in drop], obs.meta)
    fit = pyroorb.fit_orbit(subset)
    ca = pyroorb.close_approaches(fit, "2024-06-28", "2024-07-01", uncertainty=False)
    distances.append(ca[0]["distance_au"] * 149_597_870.7)   # km
```

Each refit of 2024 MK's 843 observations takes a few seconds on a laptop, so 200 of them
take a coffee break, not a week.

### Why having the whole stack in Python matters

- **Experiments become code.** Jackknife, bootstrap and leave-one-out runs, sensitivity to
  weights or arc length: the standard tools of statistics need many refits. When the fit is
  a function, each one is a few lines of numpy and pandas around a loop.
- **Nothing gets lost in translation.** The orbit you propagate is the one you fitted. It uses
  the same force model (planets, the Moon, relativity, the asteroid perturbers,
  non-gravitational forces), and its uncertainties come from the fit's own covariance.
  Nothing is exported and re-imported in another frame, epoch, time scale or element set,
  no digits are lost in a text file, and you never have to wonder which perturbers the other
  program had switched on.
- **The notebook is the record.** It shows which observations were used, which were excluded
  and why, which model was chosen, and every number that follows. A colleague who re-runs it
  gets the same chain of reasoning, not a description of what was clicked in a GUI.
- **Everything is open to inspection.** Residuals, weights, the observations the fit
  rejected and the covariance are Python objects. You can plot them, filter them and
  question them; they are not columns in another program's output file.
- **One toolchain.** There is no Fortran build, no second program to install and no
  configuration files in their own format. The only compiled code is the ASSIST/REBOUND
  integrator, which installs as a Python package (pip compiles it; conda-forge ships it
  pre-built).

Find_Orb and OrbFit remain the reference codes, and PyRoOrb builds openly on them; every
notebook below also checks its answer against JPL. What PyRoOrb adds is that the
observations, the fit and the science all live in the same Python session.

## The notebooks

These notebooks are **examples**: short, worked science questions that PyRoOrb answers in a
handful of lines, starting from the raw astrometry. Each one asks a question, fits the orbit(s)
from the observations, and **checks the answer against JPL's published values**. Where PyRoOrb
and JPL differ, the notebook says by how much and why.

They are demonstrations, not a test suite or a tutorial on every option. The supported Python
API is listed in [`docs/api.rst`](../docs/api.rst) (units and time scales:
[`docs/conventions.rst`](../docs/conventions.rst)). The notebooks use that API and nothing
else (a test enforces it): what they need beyond it they compute in a few lines themselves, or
take from numpy, astropy and JPL's services.

## Running them

The notebooks need a few packages the engine does not: matplotlib, pandas and JupyterLab.
The `notebooks` extra installs them. With the install script, which also downloads the reference
tables (`--asteroids` adds the 16-asteroid perturber kernel, ~600 MB, used by 01, 02, 04, 11, 12, 16 and 20):

```bash
./install.sh --extras notebooks --asteroids
jupyter lab notebooks/
```

Or by hand, in a clone of the repository (the notebooks are not part of the installed package):

```bash
git clone https://github.com/petervanwylen/PyRoOrb && cd PyRoOrb
uv venv && uv pip install -e ".[notebooks]"
source .venv/bin/activate
pyroorb-fetch-data --asteroids   # DE440, the debias tables and the asteroid kernel (once)
jupyter lab notebooks/
```

Already installed? Re-run the script with `--extras notebooks`, or run
`uv pip install -e ".[notebooks]"` in the clone. More install options:
[`docs/INSTALL.md`](../docs/INSTALL.md#the-notebooks-extra).

The notebooks need network access: observations come from the Minor Planet Center, and the
comparisons query JPL's public APIs (SBDB, close-approach data, Horizons, Sentry, fireballs). One
exception: the MPC has withdrawn 2020 SO's observations, so 17 reads them from Project Pluto's
archived pseudo-MPEC page. Most run in a few minutes (up to about ten) on a laptop; 15, 19 and 20
take ten to fifteen, and 13 fits sixteen orbits to multi-thousand-observation arcs
and takes half an hour or more (37 minutes on the machine that last ran it). The committed copies include their outputs, so you can read them
without running anything. Re-running them later uses newer observations, so the numbers can
shift a little.
